# Decisiones de producto y técnica — Digraf

Este documento registra decisiones confirmadas. Actualizarlo cuando se cierre una decisión durable; no usarlo como lista de ideas.

## Confirmadas

| Decisión               | Estado           | Nota                                                                                                                                                                                                                                                |
| ---------------------- | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Stack                  | Confirmada       | Next.js 16 estable, TypeScript, Supabase, Tailwind/shadcn, Zustand, dnd-kit y Vercel.                                                                                                                                                               |
| Cuentas internas       | Confirmada       | Solo Super admin crea cuentas y credenciales. Define el email y una contraseña temporal que el usuario debe cambiar en su primer ingreso; no hay registro público interno.                                                                          |
| Gestión de credenciales | Confirmada      | Super admin puede activar, desactivar y restablecer la contraseña de cualquier usuario. Un restablecimiento vuelve a exigir cambio de contraseña. Admin no crea cuentas ni asigna o restablece credenciales.                                       |
| Cambios de rol         | Confirmada       | Admin puede cambiar roles únicamente entre Atención y Empleado y puede desactivar esos usuarios. Nadie puede elevar su propio privilegio y no se puede desactivar o degradar al último Super admin activo.                                           |
| Bootstrap Super admin  | Confirmada       | El primer Super admin de cada entorno lo crea manualmente un desarrollador autorizado, como excepción inicial documentada. Crea Auth y perfil `super_admin` activo con cambio obligatorio de contraseña; los usuarios reales remotos requieren autorización explícita. |
| Contraseñas internas    | Confirmada       | Mínimo 8 caracteres y al menos un número. No se exigen otros requisitos de composición salvo los necesarios para Supabase Auth. |
| Identidad visible       | Confirmada       | Cada perfil interno tiene un nombre descriptivo para la gestión y trazabilidad; el email continúa siendo la credencial de Auth. |
| Cliente                | Confirmada       | En MVP es solo un nombre de texto en el pedido.                                                                                                                                                                                                     |
| Alta manual de pedidos | Confirmada       | Super admin, Admin y Atención pueden crear pedidos manuales. Empleado no puede crearlos ni recibe permisos adicionales por M3.                                                                                                                     |
| Tablero                | Confirmada       | Kanban estilo Trello.                                                                                                                                                                                                                               |
| Imágenes               | Confirmada       | Una imagen vigente por pedido en MVP, incorporada en M7; el alta de M3 puede existir sin imagen.                                                                                                                                                   |
| Catálogos              | Confirmada       | Listas simples, sin precios. Los moldes superiores e inferiores son tipos separados. Los ítems se borran físicamente y los pedidos conservan el snapshot histórico de sus selecciones.                                                        |
| Especificaciones M3    | Confirmada       | Conjunto requiere prenda superior e inferior, cuello, moldes superior e inferior y tela. Prenda individual requiere prenda superior o inferior, su molde y tela; el cuello aplica solo a superior. Extras son opcionales y múltiples.          |
| Importes del pedido    | Confirmada       | `total_amount`, `deposit_amount` y `deposit_paid`; saldo calculado como total menos seña solo cuando está pagada, y total completo cuando no lo está. Importes `numeric(14,2)`, seña desde cero y caja registra el total completo al pagar. |
| Visibilidad financiera | Confirmada       | Super admin, Admin y Atención pueden ver total, seña y saldo visible. Empleado no puede leer datos financieros del pedido.                                                                                                                         |
| Pago                   | Confirmada       | La seña es informativa; al pasar a Pagado se registra un único ingreso por el total completo.                                                                                                                                                       |
| Pagado y entregado     | Confirmada       | Son estados independientes; un pedido puede estar pagado sin estar entregado.                                                                                                                                                                       |
| Caja                   | Confirmada       | Tiene saldo inicial editable mientras está abierta y saldo final calculado al cierre.                                                                                                                                                               |
| Cierre de caja         | Confirmada       | Automático al iniciar el siguiente día; Admin puede cerrar manualmente. Atención no cierra.                                                                                                                                                         |
| Anulación de pedidos   | Confirmada       | Archivo exclusivo de Admin/Super admin por 30 días, restaurable o eliminable antes del vencimiento.                                                                                                                                                 |
| Formulario de clientes | Posterior al MVP | Enlace único al cliente; será la primera fase posterior al MVP.                                                                                                                                                                                     |
| Cotizador interno      | Confirmada       | Admin y Atención pueden cotizar. Solo Super admin administra precios. Calcula productos unitarios por cantidad, adicionales TPU y banderas desde una base de 1 m × 1,5 m. Genera PDF descargable sin historial ni persistencia de cotizaciones/PDF. |
| Sistema visual         | Confirmada       | Dirección “Registro de taller”, profesional y operativa. Inter para interfaz y Source Code Pro para datos mediante `next/font/google`; primera implementación solo light; mobile prioriza registros apilados; dark queda diferido. Los tokens y componentes se documentan en `docs/agent-guides/design-system.md`. |
| Fondo operativo         | Confirmada       | El canvas, el shell y la sidebar usan `#F6F8F6` (`oklch(0.9771 0.0034 145.55)`) para reducir deslumbramiento. Cards y popovers permanecen blancos y no se crean colores diferentes por pantalla. |
| Confirmación sensible   | Confirmada       | Activar, desactivar, cambiar permisos, restablecer credenciales, anular, eliminar y operaciones equivalentes requieren dos pasos mediante AlertDialog. El diálogo identifica entidad, consecuencia y reversibilidad; la UI no reemplaza autorización ni auditoría de servidor. |
| Feedback de mutaciones  | Confirmada       | Toda mutación muestra toast accesible de éxito o error, conserva errores inline de formularios y bloquea doble envío mientras está pendiente. Las operaciones sujetas a archivo, anulación o retención no se convierten en borrado físico. |
| Movimientos M4 y `paid` | Confirmada       | M4 permite solo movimientos no financieros. Hasta M11/M12 se rechaza toda transición hacia o desde la etapa semántica `paid` para cualquier rol; `delivered` continúa siendo alcanzable sin pago. Cada movimiento M4 usa transición esperada e idempotencia, y registra un único evento atómico. |
| Reversión de pago M12   | Confirmada       | La única entrada es `reverse_order_payment`, disponible para Admin/Super admin. Requiere caja abierta si el importe es positivo y crea una contrapartida `expense` enlazada sin borrar el ingreso; restaura la etapa previa registrada. La reversión exige reconfirmación, admite motivo opcional y permite reconfirmar luego con un pago activo nuevo. Un importe cero no requiere caja ni crea movimiento. Se mantienen las protecciones M10 sobre movimientos vinculados. La entrega se acepta como `size:exception` de revisión, no como regla de dominio. |
| Administración de etapas M8 | Confirmada | Super admin y Admin crean etapas ordinarias activas al final, luego reordenables. `received`, `paid` y `delivered` permanecen activas y conservan su código; una etapa con pedidos no se retira y debe quedar al menos una etapa ordinaria activa. Los eventos nuevos guardan el snapshot del nombre de origen y destino; los anteriores continúan mostrando el nombre actual. |
| Entornos y preview/staging | Confirmada       | Supabase Cloud `digraf-staging` y Vercel `digraf-staging` son los únicos entornos no locales. `staging` se crea desde `develop`, se mantiene como Preview branch protegida con Vercel Authentication y nunca se promueve a producción. `main` no se despliega en este proyecto. Producción futura tendrá proyectos Vercel y Supabase separados; staging nunca se reutiliza como producción. |
| Imágenes M7 / D-08 | Confirmada | El bucket privado `order-designs` mantiene una imagen vigente por pedido en paths no adivinables `orders/{order_id}/{uuid}.{ext}`. Solo Super admin, Admin y Atención cargan o reemplazan JPEG, PNG o WebP de hasta 10 MiB. La metadata se confirma mediante RPC transaccional e idempotente, invocable solo por la Server Action después de validar los bytes reales; no hay URLs públicas ni URLs firmadas persistidas y no se quita una imagen sin reemplazo. Los candidatos no confirmados vencen al alcanzar los 60 minutos para no competir con la reconciliación; si falla la limpieza posterior, la referencia nueva sigue vigente y el objeto anterior queda como huérfano recuperable. |
| Datos sintéticos | Confirmada       | En staging y previews solo datos sintéticos. Convención de nombres `STG-<rama>-<fecha>-<caso>` y correos `@example.test`. Ningún dato real en commits, logs, tickets, migraciones ni Trello. |
| Custodia de secretos | Confirmada       | Secretos de migración y Vercel solo fuera del repositorio: gestor personal, GitHub Environment `staging` (con `SUPABASE_ACCESS_TOKEN`, project ref y db password) y Vercel Project Settings. Ningún secreto en Git, Trello, logs, builds ni en variables `NEXT_PUBLIC_*`. `SUPABASE_SERVICE_ROLE_KEY` queda solo server-side; nunca se usa en pruebas funcionales. |
| Migraciones de staging | Confirmada       | `supabase db push` se aplica únicamente por ejecución manual autorizada contra el project ref de staging. Dry-run obligatorio antes de cada push. Ninguna preview aplica migraciones. `supabase db reset --linked` y SQL de esquema desde el Dashboard están prohibidos. La recuperación esperada es reconstruir el proyecto desde migraciones y bootstrap, porque el plan gratuito no ofrece PITR. |
| Cuentas sintéticas de staging | Confirmada       | El modo remoto `--all-roles --confirm-remote` del bootstrap existente puede crear o actualizar únicamente cuatro cuentas `@example.test` para `super_admin`, `admin`, `attention` y `employee`, exclusivamente en `digraf-staging`. Son fixtures estables con `must_change_password = false` para validar Auth/RLS; no representan usuarios reales ni crean datos operativos. |

Las contraseñas pertenecen exclusivamente a Supabase Auth: no se guardan en perfiles, tablas de auditoría ni logs de la aplicación. La desactivación debe cortar el acceso a datos protegidos aunque el usuario conserve una sesión previa.

El bootstrap administrativo recibe credenciales por variables de entorno o entrada interactiva, las comunica fuera de la aplicación y usa una clave privilegiada solo en ejecución server-side. Las cuentas creadas por este flujo se confirman automáticamente; no hay confirmación por email ni recuperación pública en M1. Si Auth y perfil quedan desincronizados, el procedimiento debe informar el estado y permitir reparar el perfil o limpiar Auth con confirmación explícita, sin ocultar huérfanos.
